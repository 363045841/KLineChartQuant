## 2. 渲染侧关键决策

- **填充颜色语义**：`PlotFill.colors` 一律按 `Plot.data` 的 bar 下标定义（不含 offset），渲染时用 `from.plot.offset` 减回位移。这是颜色错位与位移未来区丢色的根因。
- **填充走数据空间**：填充带用 `band` + `bandTriangles` 直接出网格，不再逐四边形走 stencil；同色相邻带子合并（只合并同朝向四边形，交点处断开）。
- **网格顶点存逻辑像素**：新增 `mode` 标记（`1` = 数据空间：世界 x、价格 y），由着色器应用 `DataTransform` 后归一化。此前顶点按 NDC 存储又二次归一化，会让填充整段消失。
- **顶点复用**：数据空间填充在 `prepare` 阶段整段复用顶点与 draw，`changed.vertices === false` 时零上传（`uploadsPerFrame` 保持 0）。
- **指标 Worker 拆除**：`chartIndicatorManager` 增加 `destroyed` 守卫，避免图表销毁时 `Indicator Worker executor is disposed` 触发降级与重试。

效果：10k bar 的 Ichimoku 填充从约 11.9 / 14.9 ms 降到约 4.0 / 2.6 ms；WebGPU 10k 稳定 200 FPS。

## 3. 基准方法论

- **多轮合并**：`--rounds=N` 连续测 N 轮，把全部采样帧合并后再取百分位（不是对各轮 P50 取中位数）。整机占用会让某一轮整段偏慢，单轮数据会画出假拐点。
- **异常点补测**：单轮模式下，明显高于两侧 bar 的孤立点自动补测 2 次（`[stabilize]` 前缀输出），`KLINE_BENCH_RETRIES=0` 关闭。
- **采样预算**：可见 bar ≥ 2,000 时采样帧从 300 降到 120，控制总时长。
- **进度输出**：启动阶段（Vite / Chrome / GPU 检查 / 刷新率校准）、每个场景、异常点补测、出图阶段都有日志；单场景执行期间每秒打一个点，长场景不会看起来卡死。
- **一条命令**：`pnpm bench:report` = 跑基准 → `plot.py` → `promo.py` → `promo.py --profile=ichimoku`；`--charts-only` 只重画图。
- 常用复现：
  ```powershell
  node bench/run.mjs --profiles=lines12 --rounds=3
  node bench/run.mjs --profiles=ichimoku --rounds=3
  node bench/report.mjs --charts-only
  ```
