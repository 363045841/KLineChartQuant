# 响应式派生状态：按需求值 + 提交时通知

`packages/core/src/foundation/reactivity/signal.ts` 是图表状态的唯一响应式原语。这里定义派生值如何结算，以及命令层可以依赖什么。

## 事实来源

- **原始 signal 是唯一的可写事实。** 只有 Actions 通过 `set` 写入；对外一律是 `ReadonlySignal`。
- **派生值（`computed`）不是第二份状态。** 它没有自己的提交时机：上游写入只把派生标脏并同步向整条派生链传播失效，读取时（含 `peek`）按当前输入重算。
- **`batch` 只合并通知。** 批内读取派生得到的已经是当前输入推导出的值，不存在"派生尚未提交"的时间窗。

## 提交语义

1. 原始 `set` 同步写入值，同步使所有下游派生失效。
2. 订阅者通知进入队列；`batch` 内不立即执行，最外层 `batch` 退出（或非批处理的写入结束）时统一提交。
3. 提交时按派生链结算最终值；只有值真正变化（`Object.is`）才通知下游。
4. 一次提交内每个订阅者（含 `effect`）只收到一次通知；提交过程中产生的新写入开启新一轮通知。
5. 订阅者抛出的异常被隔离，其余订阅者仍收到已提交状态。

由此得到两条可以直接依赖的规则：

- 任何时刻读到的派生值，都是当前原始状态推导出的值。
- 订阅者收到通知时读到的原始值与派生值属于同一帧，不会出现"半提交"快照。

## 命令层约定

命令与 Action 不读派生出来的呈现数据来反解状态：

- 写入 = 原始输入 + 纯投影 → 目标快照 → 一次写入（如 `applyZoom` 先投影目标档位的网格，再同时提交缩放与导航）。
- 定位用模型坐标（`scroll` / `grid.step` / `scrollBounds`），不用 DOM 滚动像素（`domScroll` / `domOffset` / `contentWidth`）；后者是渲染输出，只服务于滚动容器。
- 跨步骤有依赖时不需要额外的顺序约束：派生值会按读取时的输入重算。仍在"先写后读"里包一层 `batch` 也安全。

## 不变量

- 派生链不得循环读取自身：`computed` 在读回自身时抛错。
- 派生函数必须是纯函数；副作用只存在于 `effect`。
- `peek` 与直接读取语义一致（都按需重算），区别只在于是否登记依赖。
