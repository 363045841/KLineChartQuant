# 行情落盘缓存（IndexedDB）

状态：已实现，2026-11-13。实现在 `packages/core/src/data/buffer/impl/indexedDbBarStore.ts`，接线在 `marketDataCache.ts`。

## 目标

跨会话复用 Provider 返回的 K 线页，让「浏览过的品种」第二次打开不再等网络。

实测（ego lite，币安 BTCUSDT.P / 4 小时，CHAN + SVP + PVP 同时挂载）：

| 场景 | 请求次数 | 总耗时 |
| --- | --- | --- |
| 冷启动 | 14 | 8.3 秒 |
| 第二次打开 | 1 | 1.1 秒 |

剩下的 1 次请求是主图最新页，用来校验上游是否修正历史，属于必要成本。

## 为什么落数据层，不落指标结果

- 缓存键清晰：数据源 + 品种 + 周期 + 复权 + 聚合。指标结果还要叠加参数、脚本 revision、数据 revision，任一项变化就整段作废。
- 收益在取数：明细页一次要 13 次请求、4.6 秒；脚本计算是毫秒到百毫秒级。
- 一处实现多处受益：主图、预加载、`request.security_lower_tf` 的 1 分钟明细、缠论历史，都走同一条缓存。

## 结构

- 数据库 `@363045841yyt/klinechart-market-data`，版本 1；仓库 `bar-pages`，主键 `selectionKey|页内最早时间戳`，索引 `selectionKey`。
- 页记录：`selectionKey`、`firstTimestamp`、`lastTimestamp`、`bars`、`meta`（sourceId + instrument + series）、`olderData`、`savedAt`。
- `meta` 让读盘后能直接重建 `CacheEntry`，不需要重新请求品种目录。
- 读取按时间戳切片：游标落在页中间时只取游标之前的部分，不整页丢弃；不足 `limit` 视为未命中。

## 容量与淘汰

- 每个选择身份最多 400 页（500 根一页时约 20 万根）。
- 全局最多 2000 页，超出按 `savedAt` 淘汰最旧的。
- 历史页有效期 7 天。
- 内存缓存上限仍是每图 50 MiB（可配 5–512 MiB），落盘不影响这条策略。
- 落盘占用按页估算并写入记录（`bytes` 字段），统计时直接求和，不反复序列化。占用值通过 `MarketDataCacheStats.diskBytes` 发布，设置面板的「当前用量」同时显示内存与落盘。

## 正确性

1. **最新页每次回源校验**：命中落盘后仍请求一次最新页；它与落盘重叠的时间戳取值不同，就判定上游修正历史。
2. **写盘时比对**：新页与已存页在相同时间戳上 O/H/L/C/V 任一不同，`write` 返回 `corrected: true`，并整体作废该选择身份的落盘页，只保留新页。缓存层据此把内存条目换成新值，并递增查询 revision。
3. **形成中的 bar 不算修正**：比较时跳过新页最新一根（可能还未收线），否则每次加载都会误判成修正并清空缓存。
4. **深历史抽样校验**：命中超过 24 小时的落盘页时，本会话对该选择抽一次最旧页回源比对（每选择一次），发现差异就整段作废。
5. **手动校验入口**：设置面板「数据源」页的「校验历史缓存」按钮调用 `MarketDataCache.verifyPersistent()`，逐页回源比对全部已落盘选择；命中修正后整体作废，交给下次加载重新取。
6. **TTL 兜底**：7 天后过期重取；开发期随时可以点「清除缓存」。
7. **自动校验**：图表打开期间每 60 秒回源一次正在使用的最新页（`verifyActive`），页面隐藏时跳过；命中修正就作废落盘页并递增查询 revision，图表自动重取。定时器随缓存 `destroy()` 一起清理。
8. **降级**：IndexedDB 不可用、读写失败都按未命中处理，绝不阻断网络取数；落盘只是加速层。

## 与 TradingView 的对照

TradingView 的图表库本身只在内存里缓存 bar，靠 `noData` / `no_data` 判断历史是否取完，并提供 `resetCache` 清空；持久化一概交给数据源方实现。本实现沿用同一套语义（`olderData: exhausted` 已经是既有契约），只是把持久化放在数据层，并补上修正检测与清除入口。

## 明确不做

- 不缓存指标计算结果。
- 不做后台同步或跨标签页锁：两个标签页同时写同一选择时，后写覆盖，语义仍是「最近一次取到的值」。
- 不做按品种的手动预热：预加载由 `preloadHistory(pages)` 在添加指标时触发。

## 已知限制

- 写盘在取数关键路径上（毫秒级），换来缓存内容与请求顺序一致，便于测试与排错。
- 手动校验的耗时与落盘页数成正比（每页一次请求），界面上没有进度提示。
- 抽样校验每会话每选择只做一次，检测不到本篇未命中的修正；自动校验只覆盖「最新页」，深历史仍靠手动「校验历史缓存」与 TTL 兜底。

## 验证与排障

改动行情、缓存、明细窗口、会话配置或指标脚本后，验证前固定三步：

1. 重启对应连接器（8090 MT5 / 8091 Binance），保证后端是新代码。
2. 清缓存：设置 → 数据源 → 清除缓存；或用 DevTools → Application → IndexedDB 删除 `@363045841yyt/klinechart-market-data`。
3. 硬刷新页面。

2026-11-16 的教训：落盘缓存上线后，旧构建写入的行情页会和新代码一起被读出。数据与后端不一致时，现象是「脚本产出正确但图上显示不全」，与指标逻辑无关；不清缓存会让每次修复都被同一份旧数据盖住，形成反复修改仍不解决的假象。同一天确认：重启后端 + 清缓存后 SVP/PVP 完全正常。
