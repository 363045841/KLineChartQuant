# 行情分页补洞：整段重建而不是拒绝

## 背景

`KLineDataStore.mergePage` 原本把「落在首尾之间、却是新时间戳」的分页条目视为数据源违约，直接抛
`RangeError('分页不能插入既有序列内部')`。

这个假设在落盘缓存上线后不成立：

- `createIndexedDbBarStore().read()` 把多页记录按 timestamp 去重合并后返回，**不校验区间连续性**；
- 页按「保存时间」淘汰，不同 selection 的页覆盖区间可能不连续；
- 远端历史也会补齐或修正已经存在的时间段。

任何一条都会让缓存序列中间留下缺口。后续网络分页补上缺口时，旧实现抛错，指标整体失败，界面上显示
「分页不能插入既有序列内部」。

## 决定

内部补洞走 `replace`：把现有序列与本次页合并、排序去重后整段重建，序号从 0 重新开始，发布
`DATA_CHANGE_KINDS.replace`。

理由：补一根会改变它之后所有 bar 的序号，而序号（ordinal）是绘图锚点的定位依据。增量提交无法表达
「后续全部后移」，只有整段重建能保持序号与序列一致。

## 代价

- 一次补洞触发一次全量重绘。补洞是低频事件（缓存缺口或远端补齐历史），可以接受。
- `origin` 归零，与 `replace()` 的语义一致；调用方本来就要按 replace 重建。

## 否决的备选

1. **允许内部插入并保留旧序号**：序号会与数组下标错位，绘图锚点静默错位，比报错更难发现。
2. **只在缓存层做连续性校验**：挡不住远端补齐历史，且会让缓存命中率下降。
3. **捕获异常后 replace 重试**：异常跨多层传播，重试路径比在数据层一次判定更难维护。

## 验证

- `packages/core/src/data/__tests__/kLineDataStore.test.ts` 新增「分页补上既有区间内部的缺口时整段重建」：
  断言发布一次 `replace`、序列为有序并集、补洞后的序号正确。
- 原用例「分页插入既有区间内部时直接拒绝」删除——它把当时的错误决定固化成了守门员。
