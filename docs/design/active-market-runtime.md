# 活动行情就绪驱动

## 问题

K 线实时订阅此前由 Controller 监听 `currentSpec`，成交订阅由 DataManager 在品种、数据与视口通知中手动协调。来源探测更新普通对象属性，不触发 Controller；正式品种信息又晚于首次数据通知保存。不同消费者读取不同阶段的信息，造成 K 线订阅漏启动、成交订阅第一次拖动后重建。

## 统一状态与职责

Kernel 数据状态增加 `readyMarket`，null 表示非 K 线视图或活动来源尚未确认。就绪快照包含活动序列选择、正式品种和来源能力。`applyActiveBufferSnapshot` 一次发布活动数据和就绪来源，避免消费者看见两者不一致的中间态。

DataManager 负责加载与确认来源。先保存正式描述和能力，再发布数据；已加载缓存切回时，从相同 Buffer 恢复就绪快照。普通实时更新、历史分页和视口移动保持快照身份稳定。没有正式来源的内联数据不启动外部行情连接。

`MarketRuntime` 是一个图表唯一的网络订阅运行模块，订阅 `readyMarket` 并读取挂载时的当前值。就绪后按能力启动 K 线流，按指标需求启动成交流。Controller 仅委托操作，原有 `BarsLiveSubscription` 及其公共导出移除，避免保留第二套订阅路径。

## 接入范围

| 链路 | 驱动与生命周期 |
| --- | --- |
| 首屏 K 线 REST、自动来源解析 | 品种选择发起加载；解析结果先保存，再原子发布就绪状态 |
| K 线 SSE | 就绪状态驱动；回调捕获所属会话，失去写入资格后不能写新序列 |
| 成交 SSE | 就绪状态与指标需求共同驱动；视口移动不创建连接 |
| 成交历史 REST | 就绪行情下的视口和数据范围驱动，取消尚未发出的旧需求；请求取消由 TradeBuffer 管理 |
| K 线历史分页、比较品种加载 | 继续由可见缺口发起；每个 Buffer 的请求令牌阻止被替代或销毁后的请求发布结果 |
| 单日和多日分时 REST | 不启动 K 线或成交流；同样校验请求令牌和 Buffer 所属关系 |
| 交易日历 REST | 使用已确认来源和当前尾部锚点；原有请求身份及 Buffer 锚点校验阻止旧日历覆盖 |
| 独立盘口 SSE | DepthConnector 显式管理 Heatmap 生命周期，先挂载监听再连接；没有能力探测漏触发，不强行挂到活动 K 线就绪状态。预览盘口演示固定 BTCUSDT，不是活动品种订阅 |

## 切换与销毁

切换主行情先撤销旧就绪状态。旧连接停止时即使冲刷收线帧，也因会话身份不匹配而无法写入新 Buffer。销毁先关闭运行模块的写入资格、监听、连接与历史请求，再释放 Repository。晚返回的 REST 请求由销毁状态与每个 Buffer 的请求令牌拦截。

就绪快照可以长期读取，避免只发送一次事件导致后挂载消费者漏接。这里使用现有 Signal 的 subscribe 和原子 Action，不引入全局事件总线或新的状态镜像。

## 手动验证

按本次用户要求不执行测试套件。浏览器进入 Binance K 线视图后应出现 `/stream?...period=...`；启用足迹后额外出现 `/trades/stream`。拖动只补拉历史请求，两条 SSE 不重建。切换周期后 K 线流使用新周期，跨周期边界新增 K 线；切换品种后旧回调不能写入新图表。进入分时或销毁图表时关闭这两类活动订阅。
